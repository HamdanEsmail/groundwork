# Groundwork build log

What changed from the plan (`docs/plans/2026-11-03-groundwork-core.md`) while I built it, why, and every live TinyFish call I made during the build with its cost.

## Live reads, 9 November

Three faults showed up against the real city sites.

1. **Empty atlas tabs were kept.** `fetchAtlas` retried a still-loading page but returned at once on any read error. On live dossiers the reader answered `empty_content` for one of three tabs read together, in two of five builds; the same tab read alone a moment later was complete every time. Transient failures (`empty_content`, `no_result`, `fetch_failed`, `bad_json`, a timeout code, HTTP 429 or 5xx, a thrown network error) now share the existing `FETCH_RETRY_ON_LOADING` retries and `FETCH_RETRY_DELAY_MS` waits with incomplete pages. A definite answer (other 4xx, `target_unreachable`, an unknown code) is still returned at once. After the last retry the error is the last one seen.

2. **Evidence screenshots were cut off.** One screenshot took 11 to 26 seconds on real pages; the four run one after another, about a minute in all. Work passed to `waitUntil` has 30 seconds after the response, so later shots would be killed and the remote browser never closed. Screenshots now run as Workflow steps `evidence:<section id>` (no retries, two-minute timeout), one instance per dossier (`<id>-ev-<8 hex>`, `evidence: true`, empty `sections`). That instance does not write `workflow_id` / `workflow_started_at` and does not run `finish`. A failed create is logged by error name only; evidence stays optional. The `defer` / `waitUntil` path is gone.

3. **A street with no house number looked like the atlas was down.** `POST /api/dossiers` with `{"address":"market st"}` waited 30 seconds and answered 502 `atlas_unavailable` (`target_unreachable`). An address with no digit is now `no_match` at once, with no read, and `how_to_resolve` asks for the house number or a 9-digit OPA account.

I made no live TinyFish calls for these fixes.

## Further fixes, 9 November

1. **Spend pause after the Agent slot.** `runAgentSection` checks the pause again after the slot is held; a pause then releases the slot and marks the section `unavailable`.
2. **Timeout and poll spend.** A timed-out or unpollable run is recovered when `getRun` finds it terminal; otherwise the ledger books `AGENT_SECTION_MAX_USD` once per run id, and a later true figure replaces that row.
3. **Retry of a recorded run.** A pending section with a `run_id` is read with `getRun` (terminal: stored as a normal finish; still running: polled to the same deadline; read failure: `agent_poll_failed`) and never starts a second run.
4. **Hung evidence download.** `downloadStepScreenshot` uses `AbortSignal.timeout(POLL_TIMEOUT_MS)`; a timeout is an evidence failure, not a section failure.
5. **History and events privacy.** `GET /api/addresses/:opa/history` and `GET /api/events` return only curated parcels and parcels with an active watch, matching `/api/export.json`; an admin token sees everything.
6. **Admin-only callbacks.** Public `callback_url` on dossiers and watches is 400 `invalid_input` (callbacks need the admin token). A public dossier's callback is never copied onto a watch.
7. **Stuck partial dossiers.** Cron settles every `partial` dossier with no pending section via `dossierStatus`, and does not touch `failed`. The Workflow `finish` step has two retries.
8. **Deepen while running.** `POST /api/dossiers/:id/deepen` is 409 `in_progress` unless the dossier is `complete`. `startAgentSections` does not reset an `ok` row or a `pending` row that already has a `run_id`.
9. **Monitor order and dossier freshness.** A delivery older than `watches.last_applied_at` is recorded as a check and ignored. After a change is applied, only the newest resolved dossier for that parcel gets the new section data and read time.
10. **Unit resolution.** After the parent is read and units listed, a supplied unit (or one peeled from the address) resolves to that unit's account; no match with a list is `ambiguous` with the unit list as candidates; no list resolves as the parent.
11. **Amounts and dates.** `usd()` reads `148,232,900`, `USD 148,232,900` and `$148,232,900.00`; `usDate()` reads `1993-09-17`. Unreadable values stay null with the page text in `raw`.
12. **Open violations among shown rows.** `open_count_of` sits beside `open_count`; the report says "N open among the latest M shown; T on file."
13. **Screenshot settle.** After `Page.navigate`, the page is asked every second whether `readyState` is complete, visible text is at least 200 characters, and no line is only a loading placeholder; capture on two consecutive trues, or at 25 seconds, with `settled: boolean`.
14. **Blank evidence skipped.** An unsettled capture or an image under 12,000 bytes stores no `evidence_key`; the remote browser is still billed.
15. **Settle tests.** Fake CDP socket: settles on the third ask; never settles and captures at the deadline with `settled: false`; a tiny or unsettled image stores no key.

I made no live TinyFish calls for these fixes.

### Address normalization, resolution and retry: choices

- `src/tinyfish/client.ts` is a byte copy of Fineprint's. `src/tinyfish/fetch.ts` is Fineprint's with one added import (`limits`) and, below `fetchPage`, `AtlasTab`, `isIncomplete` and `fetchAtlas`. The `tab` union stays `property | li | zoning | deeds`; the condos link is built by swapping `/property` in the URL that served the page. *(Later changed, row 10 of the table: `AtlasTab` now also holds `condos`, and `fetchAtlas` is called for it. I later re-copied `client.ts` from Fineprint HEAD, see row 11; `fetchPage` was unchanged upstream.)*
- `normalizeAddress` (spec 4.1 step 1). Commas and periods become spaces, text is uppercased, whitespace collapsed. A trailing ZIP (5 digits, `12345-6789`, or 9 digits), `PA`, `PENNSYLVANIA` and `PHILADELPHIA` are removed in any order and number (so `... St 19107 PA Philadelphia` works), but never the last remaining token. The unit is read from the end of what is left: `#4B`, `# 4B`, `Unit 4B`, `Unit #4B`, `Apt 4B`, `Apartment 4B`, `Ste 200`, `Suite 12-A`; it needs a house number and a street before it, so `100 Suite St` is a street. A second tail strip runs after the unit is removed (`... Apt 4B, Philadelphia`). Suffix words map to the spec's forms only on the last token and only when a name token remains (`1234 Lane St` and `12 Court` keep their names). Direction words map only on the first street token and only when a street name remains beside it (`123 North Broad Street` becomes `123 N BROAD ST`; `1234 North Street` stays `1234 NORTH ST`). Only the spec's words are mapped (no `Av`, `Ctr`, `Phila`).
- `display` is the street only (uppercase, no unit); the unit is returned in `unit` and the report shows it separately. `street` and `display` are therefore equal; both exist because the interface asks for both.
- `addressVariants` = `[raw trimmed input, normalized street]`, blanks dropped, duplicates removed ignoring case (`1234 Market St` gives one variant, so the atlas is asked once). Blank input gives no variants.
- `compareResolved` splits each normalized street into house number, street name (suffix removed) and suffix. `fuzzy` when the house numbers differ, when the name's Levenshtein ratio (1 - distance / longer name) is below 0.9, or when both sides have a suffix and the two differ (`Market Ave` against `MARKET ST`). A missing suffix on either side, `Street` against `St`, and case are `exact`: `1234 Market` is what the atlas resolved to `1234 MARKET ST` in the free check, a suffix-only difference (spec 4.1 step 4: "more than suffix and case"). - Copy sources, read-only: `../standing/src/tinyfish/client.ts` (row 16 of the table), `../standing/src/tinyfish/agent.ts` (row 17), `../standing/src/tinyfish/browser.ts` (byte-identical to Fineprint's except the constant, row 18), `../standing/src/tinyfish/monitor.ts` (row 19). - `runAgentToCompletion(env, p, { pollEveryMs, maxWaitMs, sleep?, now? })`: `startRun`, then `sleep(pollEveryMs)` and `getRun(..., "none")` until the status is COMPLETED, FAILED or CANCELLED (the statuses the spikes poll on), then one `getRun(..., "url")` for the step screenshot URLs. The wait comes before each poll, so the first poll is one interval after the start. The same `sleep` goes to the start, so the 60 s waits of a rate-limited start are injectable too. `RunResult` is `{ runId, status, result, numOfSteps, error, steps, finishedAt }`; `status`, `result`, `numOfSteps`, `error` and `finishedAt` come from the terminal poll (the one the spend row is based on), `steps` from the screenshot read.
- Spend rule: when the run is terminal, one `agent_step` row of `num_of_steps x PRICES.agent_step` (for the li-deep run 9 x 0.016, stored as the product, 0.14400000000000002), ref the run id. A FAILED or CANCELLED run is billed for its steps too. A terminal run with 0 steps, or one that reports no step count, writes no row (nothing was billed, and a `NaN` or `$0` row would only add noise). The row is written before the screenshot read, so a failure of that read cannot lose it. A failed ledger write is logged (`spend write failed`, `agent_step`) and the result is still returned, as `tinyfishFetch` does for its own spend notes.
- Timeout rule: `maxWaitMs` counts from the moment the run exists, not from the call (a start that waited 180 s on three 429s does not eat the run's time). After each poll that finds the run not terminal, if `now() - startedAt >= maxWaitMs` the call throws `TinyFishError(504, "agent_timeout")` (the message names the run id and the wait) and records no spend. A run that is terminal on that last poll is returned, not timed out. Callers pass a `maxWaitMs` above `AGENT_MAX_DURATION_SECONDS` (170 s), which TinyFish enforces itself.
- Failure handling: an error from the start (400, 500, `busy` after four 429s) or from a poll propagates unchanged; the run id is then lost to the caller, and a run that was already started keeps going on TinyFish's side. If only the final screenshot read fails, the result is returned with the steps of the last poll (no screenshot URLs) and `agent screenshot read failed` plus the error's name is logged.

- Slot SQL (`src/db/inflight.ts`), one statement so two concurrent calls cannot both win:
  `INSERT INTO agent_inflight (id, run_id, started_at) VALUES (1, ?1, ?2) ON CONFLICT (id) DO UPDATE SET run_id = excluded.run_id, started_at = excluded.started_at WHERE COALESCE(agent_inflight.started_at, '') < ?3 RETURNING run_id`.
  `?1` is the holder, `?2` the start time (ISO-8601 UTC), `?3` the stale cutoff, `now - AGENT_SLOT_STALE_MS`; the call returns true only when the row it gets back carries its own holder. A hold is stale when strictly older than `AGENT_SLOT_STALE_MS = 10 * 60 * 1000` (exported from `inflight.ts`; exactly ten minutes is not stale); a NULL `started_at` counts as stale so a damaged row cannot block the slot for good. `releaseAgentSlot` is `DELETE FROM agent_inflight WHERE id = 1 AND run_id = ?1`: a holder that went stale cannot free a newer holder's slot. `slotHolder(db)` returns `{ holder, startedAt }` or null.
- The slot is not re-entrant: a holder that still holds a fresh slot is told false like anyone else. A Workflow step that is retried after a crash with the same `<dossierId>:<sectionId>` token therefore waits for the stale cutoff unless the earlier attempt released the slot (callers release in a `finally`).

- **The slot rule Task 7 follows** (documented on `runAgentToCompletion`). ## Faults I found reading the code again, 10 November

1. **A visitor's watch made a private lookup public.** A visitor pressing "Watch" made a private one-off lookup public: the export, the parcel history, the events API, the home feed, the watchlist and the nearby view all counted any active watch. I changed the rule. A parcel is now public only when it has a curated dossier or an active watch set with the admin token (`PUBLIC_OPAS_SQL`, `listPublicDossiers` and `listPublicDossiersOf` in `src/db/dossiers.ts`; `src/handlers/read.ts`; `src/site/query.ts`). A visitor's own dossier is never in the export, even of a public parcel, because it carries what that visitor typed. A visitor's watch is listed on the watchlist for that visitor only, as `Yours until <day>`. A visitor may start one watch a day (`PUBLIC_WATCHES_PER_IP_PER_DAY` in `src/core/limits.ts`, claimed in `src/dossier/watch.ts` and given back when the watch is refused).
2. **The zoning reader kept contact details.** It kept each community organization's contact person with a phone number and an email, and the JSON served it. I stopped keeping that cell (`src/sections/zoning.ts`). The recorded pages in `tests/fixtures/atlas/` now carry invented contacts and an invented appeal text.
3. **A cleaned address waited 30 seconds.** An address typed with a trailing period or a city and ZIP waited 30 seconds before its cleaned form was tried, because an empty answer was retried. I changed that: while an address is being resolved, an empty answer to every form but the last is final (`emptyIsFinal` in `src/tinyfish/fetch.ts`, `src/address/resolve.ts`).
4. **A stalled Workflow failed the whole dossier.** The hourly job marked a whole dossier failed when its Workflow stalled, even with four sheets read, and a failed dossier can never be upgraded. I changed it to mark only the sheets. The dossier is complete with gaps, and failed only when no requested sheet was read (`src/cron.ts`).
5. **New data sat beside an old screenshot.** After a Monitor reported a change, the newest dossier showed the new data beside the old screenshot. I now drop the stored screenshot from that sheet, and I write the change into the dossier the watch belongs to: the newest one I added for a watch of mine, the watcher's own for a visitor's watch (`src/handlers/webhooks.ts`).
6. **Agent dates got a made-up day.** An Agent date given as only a year or a month was stored as a made-up day ("2026" became 2026-01-01). I changed `dateValue` in `src/sections/agentCommon.ts` to read only full dates. Anything less is left empty with the page's own words kept in `raw`.
7. **A TinyFish Browser was left running.** A TinyFish Browser that was made but could not be driven (no socket address, or the socket refused) was left running and billed by the minute. I now end it with `DELETE https://api.browser.tinyfish.ai/{sessionId}`, which TinyFish's API description says is safe to repeat (`src/tinyfish/browser.ts`).
8. **One picture on the home is half loaded.** `public/assets/captures/walnut-zoning.jpg` showed the city page half loaded. Replaced on 10 November with the screenshot of that sheet from the live dossier for 4001 Walnut St.

## The first live reports, and what they broke, 10 November

- **The third sheet always died.** The first two full reports stopped at their third browser read: `agent_poll_failed`, although TinyFish had finished the run and held its result, then `agent_start_uncertain` for the next. TinyFish was fine (I read one finished run 45 times in 45 seconds without a refusal). The cause was mine: one Workflow instance ran all five reads and polled every 5 seconds, and the Workers free plan allows an invocation 50 requests to other hosts. The steps that only waited for the slot also ended in "internal workflows error" after some minutes.
- **The change.** One Workflow instance for each sheet (`startAgentSections`). A try at a sheet answers "busy" at once when another holds the slot, and the Workflow sleeps 20 seconds with `step.sleep` and asks again, up to 90 times, so no step sits waiting. Polls are 10 seconds apart: a sheet is at most 24 requests. A request the platform refuses to send is now named `subrequest_limit`, frees the slot (no run exists) and says so in the section. Finishing a dossier only moves it out of `partial`, so the callback is posted once however many instances finish. Tests first for each; the five older tests that expected one Workflow per dossier were rewritten.
- **A build that outlives its caller.** My own script lost its connection mid-request and left a dossier half read: Cloudflare stops a request whose client has gone. The build is handed to `waitUntil` in both routes that start one.
- **Paid and not read.** Two school reads had been paid for ($0.048 and $0.16) and thrown away. A section that failed with `agent_poll_failed` or `agent_timeout` and has a run id is now read again from that run. `POST /api/dossiers/:id/retry` (admin) does it, for every failed sheet or the ones named. Both came back without a new run.
- **What the browser reads really return.** Of 20 runs, 9 returned what was asked. In the three reports that is 15 browser sheets: 8 read, 1 with nothing to list, 6 gaps.
  - *Valuations.* The table fills a few seconds after the page opens. Three runs read it at once and returned rows of empty cells, one of which I had stored as read. The three reports each have 13 years.
  - *Tax.* One read of three found the balance. The other two used all 15 steps finding the search link and typing into the wrong idea of the form, then called it "blocked".
